# 安心通道 · 匿名举报平台

基于 Deno + Fresh
的企业内部匿名违规举报平台。设计目标:**从技术上**(而不仅是制度上)
保证举报人不可被定位 —— 包括平台管理员在内,任何人都无法查出举报人是谁。

## 快速开始

```bash
# 开发(自动重载)
deno task start

# 创建工作人员账号(管理员 / 调查员)
deno task create-user admin 合规部管理员 admin 'Str0ng!Pass'
deno task create-user zhang 张调查 investigator 'An0ther!Pass'

# 生产运行
deno task serve
```

访问 `http://localhost:8000`。本地开发时设置 `COOKIE_SECURE=0`(HTTP 下无法种
Secure Cookie):

```bash
COOKIE_SECURE=0 deno task start
```

数据存储在本目录 `data/kv.db`(Deno KV,无需外部数据库)。备份 = 备份该文件。

## 功能

- **举报人**:免账号提交举报 → 获得一次性显示的案件凭据(编号 + 口令)→
  凭凭据查询进展、与调查人员双向匿名沟通、补充材料
- **调查员**:查看案件、回复举报人、流转状态(待受理→已受理→调查中→待补充→已结案)
- **管理员**:除调查员能力外,可将案件分派给调查员

## 哪些信息能定位到人 —— 梳理与对策

平台按以下六类梳理"可定位信息",每一类都有对应的技术对策:

### 1. 网络与传输层

| 可定位信息                       | 对策                                                                    |
| -------------------------------- | ----------------------------------------------------------------------- |
| IP 地址、`X-Forwarded-For`       | 代码中**从不读取**请求来源地址;部署文档要求反向代理关闭访问日志(见下)   |
| User-Agent、浏览器指纹           | 不读取、不存储;不加载任何第三方脚本/字体/统计(CSP `default-src 'self'`) |
| 访问时间戳(与门禁、VPN 日志关联) | 案件时间只精确到**日**,消息时间只精确到**分钟**                         |

### 2. 账户与凭据

| 可定位信息                   | 对策                                                                         |
| ---------------------------- | ---------------------------------------------------------------------------- |
| 邮箱、手机号、工号(注册信息) | **不要求任何注册**;举报人与平台的唯一纽带是随机案件凭据                      |
| 案件口令本身                 | 只存 PBKDF2(21 万次迭代)哈希,数据库泄露也无法反推;凭据丢失无法找回(这是特性) |
| 登录行为关联                 | 举报人会话是随机令牌 → 案件编号的映射,2 小时过期自动清除                     |

### 3. 提交内容

| 可定位信息                         | 对策                                                                        |
| ---------------------------------- | --------------------------------------------------------------------------- |
| 正文中写出的姓名/联系方式          | 浏览器端**实时**检测邮箱、手机号、身份证、微信号、工号并警告;服务端二次确认 |
| 图片 EXIF(GPS、设备型号、拍摄时间) | JPEG 剥离全部 APPn/COM 段,PNG 只保留解码必需块,服务器端自动完成             |
| PDF/Office 文档属性(作者、公司)    | 无法可靠自动清除 → 界面明确警示,建议举报人自行清理后再上传                  |

### 4. 浏览器与设备

| 可定位信息               | 对策                                                        |
| ------------------------ | ----------------------------------------------------------- |
| 追踪 Cookie / 第三方统计 | 全站仅两个会话 Cookie(HttpOnly + SameSite),无任何第三方资源 |
| 浏览器缓存泄露案件内容   | 全站 `Cache-Control: no-store`                              |
| Referer 泄露来源页面     | `Referrer-Policy: no-referrer`                              |

### 5. 平台内部(管理员视角)

| 可定位信息           | 对策                                                                  |
| -------------------- | --------------------------------------------------------------------- |
| 数据库中的举报人字段 | **不存在** —— 案件表没有任何与举报人相关的列,管理员看到的和调查员一样 |
| 工作人员身份反向泄露 | 举报人只能看到"调查人员",看不到工作人员姓名                           |
| 日志                 | 应用不写任何访问日志;会话、限流记录均不含来源地址                     |

### 6. 平台控制范围之外(必须告知举报人)

首页已明确提示以下残余风险,平台无法从技术侧消除:

- **写作风格识别**:语气、用词习惯可能被熟人认出
- **办公环境监控**:上网行为管理、终端 DLP、屏幕监控 —— 建议使用个人设备 +
  非办公网络
- **时间关联**:提交时间与考勤/VPN/门禁记录的关联(平台已降低时间精度,但无法完全消除)
- **知情范围**:只有少数人知道的细节本身就能缩小范围

## 部署要点

1. **反向代理必须关闭或匿名化访问日志**,否则代理层的 IP
   日志会让平台的匿名设计失效:
   ```nginx
   access_log off;  # 或仅记录不含 IP 的格式
   ```
2. 全程 HTTPS;生产环境不要设置 `COOKIE_SECURE=0`。
3. 可选:以 Tor Onion Service 形式提供访问,进一步消除网络层风险。
4. 定期备份 `data/kv.db`;该文件不含任何举报人身份信息。
5. 限流不基于 IP(全局窗口 +
   按案件/按账号桶),如需更严格的防滥用,请在**不记录来源**的前提下调整
   `lib/db.ts` 中的 `rateLimit` 参数。

## 目录结构

```
lib/crypto.ts     凭据生成、PBKDF2 哈希、时序安全比较
lib/sanitize.ts   JPEG/PNG 元数据剥离、联系方式检测(浏览器端共用)
lib/db.ts         Deno KV 数据层:案件、消息、文件、账号、会话、限流
lib/session.ts    Cookie 与重定向工具
routes/           页面与 API(举报人端 /case、工作人员端 /staff)
islands/          举报表单(浏览器端实时身份泄露检测)
scripts/          创建工作人员账号
```
