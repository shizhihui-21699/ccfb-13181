# 匿名内部举报渠道

基于 **Deno + Fresh**
的内部违规举报平台。设计目标只有一个：**举报人不必相信任何人的承诺，因为系统里没有能定位到举报人的信息。**

不是"我们保证不记录"，而是"数据库表里没有对应的列"。

---

## 一、这套系统解决什么问题

现状是把邮件发给合规部——谁发的、什么时候发的、从哪台机器发的，一目了然。员工因此不敢举报。

本系统把"匿名"做成**结构性保证**而非管理承诺：

| 威胁             | 传统邮件 | 本系统                   |
| ---------------- | -------- | ------------------------ |
| 后台能看到发件人 | 是       | **没有发件人字段**       |
| 登录即实名       | 是       | 举报侧**完全无需登录**   |
| 管理员可反查     | 是       | 管理员**看不到案件内容** |
| 附件带作者/定位  | 是       | 上传时**剥除元数据**     |
| 时间可关联门禁   | 精确到秒 | **只到天**               |
| 数据库泄露即暴露 | 是       | 只存**凭据的带密钥哈希** |

## 二、哪些信息会定位到人（完整梳理）

这是本系统的核心设计依据。清单分三类：**永久拒收**、**接收但降级**、**接收但净化**。

### 2.1 永久拒收（结构上不存在）

| 信息                          | 为什么致命                                   | 本系统做法                                       |
| ----------------------------- | -------------------------------------------- | ------------------------------------------------ |
| 姓名 / 工号 / 员工编号        | 直接实名                                     | `cases` 表无对应列                               |
| 邮箱 / 手机 / 分机            | 直接实名                                     | 无对应列                                         |
| 部门 / 汇报线                 | 缩小到个位数人群                             | 无对应列（举报人可在正文自述，属自愿）           |
| 公司账号 / SSO / 域账号       | 直接实名                                     | 举报侧无登录                                     |
| IP 地址（v4/v6）              | 结合 DHCP、VPN、代理日志定位到工位或家庭宽带 | 不读取、不写审计、不入库                         |
| User-Agent / 客户端指纹       | 设备型号+版本+字体可近似唯一                 | 不记录                                           |
| Cookie / localStorage 追踪 ID | 跨会话串联                                   | 仅用会话 Cookie，且只属于"案件"不属于"人"        |
| Referer / 来源页面            | 暴露"谁从哪个内网系统点进来"                 | `Referrer-Policy: no-referrer`，且页面无外部资源 |
| 设备 MAC / 主机名             | 直接定位设备                                 | 不采集                                           |
| 精确提交时间                  | 与门禁、打卡、排班、代理日志做时间关联       | 只存到"天"（见 2.2）                             |
| 附件原始文件名                | 常见「张三-工资条.xlsx」                     | 丢弃，服务端随机命名                             |
| 上传时的临时路径/表单字段名   | 可能含本机用户名                             | 不读取                                           |

> 反向验证：`tests/anonymity.test.ts` 会断言 `cases` 表**不存在**
> `ip`、`email`、`employee_id`、`user_agent`、`reporter_name`、`device`、`fingerprint`
> 等列。改代码加了这些列，测试会失败。

### 2.2 接收但降级：时间

**所有由举报人产生的时间，一律归零到当天（`YYYY-MM-DDT00:00:00.000Z`）。**

包括：

- 案件提交时间（`cases.created_at`、`submitted_day`）
- 举报人的每条补充消息（`messages.created_day`，且 `created_at` 必须为 `NULL`）
- 举报人触发的流转事件（回复、撤回）
- 举报人会话的创建与到期时间（到期按"天+2"锚定，不做精确倒计时）

代价：同一天内多份举报的先后顺序丢失。这是有意的——调查流程依赖"天"，不依赖"秒"。

员工侧操作（分派、状态变更、留言、下载附件）**保留精确时间**，因为员工不需要匿名，且审计需要可追溯。

> 数据库里加 `CHECK` 约束：举报人消息的 `created_day` 非空时，`created_at`
> 必须为空、`author_id` 必须为空。写错即报错。

### 2.3 接收但净化：附件

文件是最容易被忽视的"实名材料"。处理链路：

```
上传 → 按魔数判类型（不信扩展名/Content-Type）→ 剥元数据 → 服务端随机命名 → AES-256-GCM 加密落盘
```

| 类型             | 处理                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| PNG              | 丢弃所有非关键 ancillary chunk（`tEXt`/`tIME`/`eXIf`/`iTXt`/`zTXt`…），保留像素                   |
| JPEG             | 丢弃 `APP1`–`APP13`、`APP15`（EXIF/XMP/IPTC/Photoshop）与 `COM`，保留 `APP0`(JFIF)/`APP14`(Adobe) |
| WebP             | 丢弃 `EXIF`/`XMP`/`ICCP` 块，并同步清除 `VP8X` 标志位                                             |
| PDF              | 清空 Info 字典（作者/标题/主题/创建者/生产者/关键词）并删除 XMP `Metadata`                        |
| 纯文本           | UTF-8 校验 + CRLF→LF + 去 BOM                                                                     |
| **其它一律拒绝** | Office（docx/xlsx/pptx）、压缩包、HEIC、可执行文件、HTML/SVG                                      |

**为什么拒收 Office**：作者、公司、最后修改人、内网路径散落在
`docProps/core.xml`、`docProps/app.xml`、`customXml/` 等多个
part，还可能有修订记录与批注作者。纯服务端"尽力清除"不可靠，宁可要求另存为 PDF。

**诚实说明**：元数据能清，**画面内容不能**。工牌、桌上的文件、窗外景物、屏幕反光都可能指向人。这一点在提交页和隐私说明里明确告知，不做虚假承诺。

## 三、凭据机制

提交成功 → 生成 25 位 Crockford Base32 凭据（125 bit 熵）→ **只显示一次**。

- 数据库只存 `HMAC-SHA256(pepper, "credential:v1:" + 凭据)`。
- `pepper` 是 32
  字节随机密钥，存于数据目录下的独立文件（`0600`），**不在数据库里**。拿到数据库备份的人无法离线验证猜测。
- 凭据**不与任何账号关联**，因此**丢失不可找回**。这是匿名性的代价，也是前提。
- 凭据可查看进展、补充材料、撤回举报。

### 3.1 一次性交付

凭据不能进 URL（会进浏览器历史、反代日志、Referer），也不能落盘。做法：

1. 提交后服务端生成随机**交付令牌**，把令牌放进重定向 URL。
2. 凭据本体只存**进程内存**，60 秒过期、读取即销毁。
3. 交付页刷新或重放 → 跳转"链接已过期"。

## 四、角色与权限

| 角色                | 案件可见范围   | 分派 | 改状态 | 联系举报人 | 管账号 | 看审计 |
| ------------------- | -------------- | ---- | ------ | ---------- | ------ | ------ |
| 调查员 investigator | 仅分派给自己的 | ✗    | ✓      | ✓          | ✗      | ✗      |
| 负责人 lead         | 全部           | ✓    | ✓      | ✓          | ✗      | ✓      |
| 审计员 auditor      | 全部（只读）   | ✗    | ✗      | ✗          | ✗      | ✓      |
| 管理员 admin        | **无**         | ✗    | ✗      | ✗          | ✓      | ✓      |

**管理员刻意看不到案件正文**：他是"系统钥匙"，不该同时是"内容钥匙"。这条由
`canAccessCase()` 与路由双重保证，并有测试覆盖。

访问不存在的案件与无权访问的案件，**都返回 404**（不是 403），避免用 ID
探测案件是否存在。

## 五、案件流转

```
已收到 → 初核中 → 调查中 ⇄ 等待你补充 → 已处理 → 已结案
                                          ↘ 举报人可随时撤回
```

- 调查员向举报人发消息 → 自动置为「等待你补充」。
- 举报人回复 → 自动回到「调查中」。
- 内部备注（`internal_only=1`）对举报人不可见。
- 撤回：案件立即退出队列，内容保留用于合规审计（界面已说明）。


| ------------------------------ | -------------------------- | ------------------------------------------------------- |

| `WHISTLE_DB`                   | `<dataDir>/whistle.sqlite` | 数据库路径                                              |

| `WHISTLE_RETENTION_DAYS`       | `0`                        | 已结案案件保留天数，0=不自动清理                        |
| `WHISTLE_MAX_ATTACHMENT_BYTES` | `8388608`                  | 单附件上限                                              |

## 七、部署时必须做的事（否则匿名性会漏）

本系统只能保证**应用层**不记录。以下属于运维责任：

1. **关闭反向代理的访问日志**，或至少不记录请求体、不长期保存 IP。Nginx 示例：
   ```nginx
   location / {
     access_log off;                      # 关键
     proxy_pass http://127.0.0.1:8000;
     proxy_set_header X-Forwarded-Proto $scheme;
     client_max_body_size 32m;            # 略大于附件总上限
   }
   ```
2. 不要把应用部署在会做**上网行为审计**的网段，或至少在员工告知中说明网络侧仍在记录。
3. `data/` 目录权限 `0700`，数据库 `0600`；`pepper.key` 单独做离线备份。
4. 若要真正抗"运维作恶"，把应用放在合规部控制的独立主机上，而不是 IT
   通用运维池。
5. 定期跑 `deno task admin purge`，避免无限期保留。

## 八、残余风险（如实告知）

这些是系统**解决不了**的，界面里也写了：

- **网络层**：公司网络、VPN、代理的流量日志不在本系统控制内。
- **内容自我暴露**：正文细节、照片画面、只有少数人知道的信息。
- **小范围推断**：某科室只有 3 人时，内容本身就能指向人。
- **调查过程**：照着举报原文逐条问被约谈人，会间接暴露举报人。合规流程应避免。
- **存储介质**：拿到磁盘镜像 + pepper +
  数据库的人，理论上仍能通过访问模式推断（例如某天新增一条案件）。缓解手段是限制物理访问与备份权限。

## 十、技术栈

- Deno 2.9 / Fresh 2.3（服务端渲染，无客户端框架依赖）
- `node:sqlite`（WAL、`secure_delete`、外键）
- `pdf-lib`（PDF 元数据清除）
- 零前端第三方资源（CSP `default-src 'self'`，无外链字体/脚本/图片）
